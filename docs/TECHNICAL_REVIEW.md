# BLIF 网表解析优化：项目技术复盘与面试准备

更新：2026-10-28。依据当前源码及本次实测整理。

## 1. 一分钟介绍

我关注网表解析时大量重复信号名带来的内存分配开销。基线把 token 构造成 std::string，再按值传给存储函数，最后 strdup 保存；相同名字重复出现时仍反复分配。我将接口改为指针加长度，并用字符串驻留表保存唯一字符串，重复 token 直接复用已有地址。两版使用同一套 flex/bison，只替换存储模块。本次 10 万门合成网表实验，7 轮最小解析耗时从 20.227 ms 降到 17.347 ms，减少约 14.2%，模型摘要保持一致。

这是公开复现的陈述。真实业务输入、本人职责及原工作 39% 等指标，要依据本人经历和原始材料单独说明。

## 2. 编译流程与当前范围

```text
Verilog RTL → Yosys 综合 → BLIF → 词法扫描 → 语法分析 → 内部网表 → 后端模型生成
                                      本仓库聚焦
```

本仓库用 `scripts/gen_blif.py` 生成受限 BLIF 测试输入，没有调用 Yosys。bison 动作仅记录模型名、输入输出数量、门/latch 数量与信号名摘要，没有保存完整连接图和真值表，也没有 SystemC 代码生成。

与端口更新项目的关系：本仓库减少编译时解析成本，另一个仓库减少模型运行时调度成本。两者没有自动串联。

## 3. 从文件到存储的调用关系

```text
bench_main.cpp
  → model_reset / strstore_reset
  → 打开输入
  → chrono 开始
  → yyparse() [由 blif.y 生成]
      → yylex() [由 blif.l 生成]
          → strstore_intern(yytext, yyleng)
      → 执行模型计数/摘要动作
  → chrono 结束
  → 关闭输入、输出统计
```

Makefile 分别将统一 lexer/parser 和两种存储实现链接成 `blif_bench_strdup`、`blif_bench_intern`。语法规则一致，因此主要变量是存储策略；不过优化同时改变了传参和分配，不能单独把全部收益归因于某一行代码。

## 4. 为什么一个信号名会反复出现

```blif
.model demo
.inputs clk en a b
.outputs y
.names clk a n1
11 1
.names clk b n2
11 1
.names n1 n2 y
11 1
.end
```

同一信号 clk 是一个逻辑对象，却在文件中被多个门引用。高扇出控制信号会产生大量相同 token。基线按出现次数分配，驻留按不同内容数分配。

生成器固定随机种子，40% 的组合扇入选择热信号，其余偏向最近生成的信号；名字较短，能观察分配成本。当前发布修复了热信号未声明、latch 输入输出次序颠倒的问题。它仍是有利于重复字符串复用的合成负载，不能代表所有真实网表。

## 5. 基线代码做了什么

```cpp
std::string token(s, n);
return store_by_value(token);   // 参数是 std::string
// store_by_value 内部：strdup(token.c_str())
```

成本包括临时字符串构造、值传递语义以及每 token 的独立 C 字符串分配。短字符串可能使用 SSO，编译器也可能消除部分中间操作；不能笼统宣称每个 std::string 都必然堆分配。当前基线还跟踪分配地址，以便轮次之间释放，跟踪成本在计时路径内。

## 6. 驻留表如何工作

接口 `strstore_intern(const char* s, size_t n)` 直接使用 flex 已知长度，避免额外构造 std::string；第一次出现时分配 n+1 字节并补终止符，再次出现返回同一地址。

槽结构包含 hash、长度和稳定字符串地址。连续槽数组通过开放寻址、线性探测解决冲突：先算 hash 找起始槽，槽非空时比较 hash/长度/内容，不相等则前进到下一槽。

不能只比较 hash：碰撞并不意味着内容相同。当前实现还做 memcmp，避免错误复用。

本次发布在负载达到约 70% 前扩容到两倍，重新放置槽条目；字符串本体不移动，所以旧 token 指针继续有效。初始为 2^20 槽，每轮重新建立表；没有固定容量用满后无限探测的问题。

## 7. 复杂度与空间取舍

设 token 出现次数 T、唯一字符串数 U、平均长度 L：

```text
基线：约 T 次字符串分配，拷贝成本与总 token 字节数相关
驻留：约 U 次字符串分配，每次出现仍需 hash，命中时需比较
```

“平均 O(1)”只指负载受控、哈希分布合理时的槽查找/探测期望次数。字符串 hash 和比较仍需要读字节，整体并非与字符串长度无关。扩容是摊销开销；最坏碰撞仍可能退化。

空间上少存重复文本，但多了槽数组。默认 2^20 槽，在本次 64 位环境中每槽通常 24 字节，约 24 MiB，再加唯一字符串。小输入可能不划算；表大小、重复率和名字长度都需要权衡。

## 8. 生命周期为什么重要

flex 的 yytext 指向扫描器缓冲区，后续扫描会复用，不能把 yytext 原指针直接长期保存。必须复制唯一内容到由存储模块拥有的内存。

当前约定：返回指针在下一次 `strstore_reset()` 前有效。reset 释放本轮所有字符串；驻留版还释放表。调用者不能在 reset 之后继续访问旧模型里的字符串。

旧代码在 reset 时清空槽但不释放字符串，基线也未跟踪释放，会造成多轮基准累积内存。本次两版均修复了释放；手写参考也补齐所有权并在计时结束后复制需要保留的 token，避免悬空指针。

存储是进程级全局状态，当前不支持多个 parser 并发调用。若做生产化，应改为解析上下文持有的对象，并定义异常和内存不足处理。

## 9. 如何做公平测量

本次固定输入、种子、编译选项和轮数，报告最小值与中位数：

| 指标 | 基线 | 驻留 | 计算结果 |
| --- | --- | --- | --- |
| 7 轮最小耗时 | 20.227 ms | 17.347 ms | 耗时减少 14.24%，加速比约 1.166× |
| 7 轮中位耗时 | 21.007 ms | 18.921 ms | 耗时减少 9.93% |

公式：`耗时减少比例=(T_base-T_opt)/T_base`；`加速比=T_base/T_opt`。耗时减少百分比不等于吞吐增加百分比。

chrono 覆盖 yyparse，其中包含 lexer 的 stdio 读取、语法动作、字符串处理和本轮首次建表；不包含 fopen/fclose、reset 和打印。后续轮次受 OS 页缓存影响。两版分别运行，测试顺序、调频、系统负载会影响结果。更严谨的报告应多批交替运行并给出波动。

手写参考先把整文件读入，预分配 token vector 和驻留表，然后计时 tokenizer，最后比较 token。因此它与 flex/bison 的计时边界不同；本次参考的 24.0% 不能替代正式解析器的 14.2%。

若希望单独证明“传参优化”和“驻留优化”的贡献，需要加入第三版“指针+长度、每 token 分配”的消融实验。当前没有该实验，不给两项分别分配百分比。

## 10. 当前正确性证据与局限

自动验证覆盖三种网表规模，两版模型摘要一致；手写参考逐 token 比较内容；存储单测验证非终止输入切片、相同内容复用指针、74 万唯一串触发扩容、扩容后旧指针稳定及 reset。

摘要包含信号名内容，但不覆盖真值表语义，且 hash 理论上存在碰撞。摘要相同只能支持当前计数/摘要输出一致，不能证明任意电路等价。

词法/语法是受限子集：忽略部分未知字符，不处理所有 BLIF 注释、续行、转义标识符、层次子电路和错误恢复。不能直接当作任意 Yosys 输出的生产解析器。空输入也可能被极简语法接受。

## 11. 旧结果如何在面试中使用

原材料写过“blifParse 占 92.7%、提升 39%”；旧复现 README 写过 flex/bison 26–27%、手写 39%。这些属于历史背景，输入、基线和生命周期策略与本次发布不同，不应写成当前版本的验证结果。

本仓库能直接证明的是：当前输入和构建下，两种存储策略产生相同摘要；本次测得上述耗时变化。对于真实业务提升 39%，需要原始日志、计时范围、数据规模和指标定义支持。

## 12. 常见追问

**与 std::string_view 有什么区别？** string_view 只是一段非拥有视图，不负责让 lexer 缓冲区永久有效。驻留表需要拥有稳定字符串内存。

**为什么不直接 unordered_map<string, string>？** 会重复保存 key/value 内容，节点和分配成本也较高。当前开放寻址可控制布局；不过没有与所有标准容器实测，不能声称总是最快。

**重复率低会怎样？** U 接近 T 时，几乎省不掉字符串分配，却多了 hash、比较和槽数组，可能变慢。

**名字长就一定更好吗？** 不一定。基线拷贝更贵，但驻留仍要计算 hash、比较内容；最终受长度、重复率、缓存和 allocator 影响。

**为什么不用内存池？** 可以把多个唯一字符串放到 arena，减少 allocator 调用；与驻留互补。当前是每个唯一字符串 malloc，尚未实现块式 arena。

**会不会把同名但不同作用域的信号合并？** 当前只复用文本存储，不把文字相同自动当成同一逻辑节点。若构造真实符号表，需要同时考虑作用域/模块名。

**如何进一步优化和验证？** 增加真实匿名网表、多种重复率/长度输入、峰值内存数据、消融版本、完整结构比较与 parser 模糊测试，再决定表大小、arena 和 hash。
